          Methodology how this world is built, and why

          Intent

          A daily, unattended, credible read on cybersecurity in the energy sector, worldwide with a United States focus, that you can interrogate instead of scroll. The town metaphor is not decoration: each resident is one analytic job, and giving the jobs to different agents is what makes them disagree, which is where the analysis comes from.

          The loop (runs twice a day, no button to press)

          1. Fetch. Only the feeds in sources.json are read. Each carries a bias note. Nothing outside the allowlist enters.
          2. Make relevance. A story is energy-cyber only if it has both an energy signal (grid, pipeline, utility, ICS vendor, substation…) and a cyber signal (breach, CVE, ransomware, exploit…). Everything else from the same window is kept in a "wide" bucket so the Wide-Angle can see what else was happening.
          3. Curate. Six analytic residents each write a briefing over the same bundle: the Reporter (what happened, confirmed vs claimed), the Analyst (actor, tradecraft, IT vs OT), the Media Critic (bias of each outlet), the Wide-Angle (simultaneous events that could spill over), the Contrarian (who was not affected), and the Verifier (audit). The Librarian keeps the map of where to look.
          4. Ledger. Every kept story becomes one structured record: event core, energy subsector and value-chain segment, IT-versus-OT impact (the most important single field), actor and attribution confidence, CVE, impact, geopolitical and regulatory context, Admiralty-style source reliability (A–F) and credibility (1–6), so-what, recommended action.
          5. Pull the direct source. Every URL behind every item is fetched; links to primary documents (CISA, FERC, NERC, TSA, vendor advisories, victim statements) are followed and fetched too.
          6. Verify one against the other. For each item the outlet's claim is set beside the primary text: agree, differ, verdict. Items are corrected where the primary disagrees (CVE ids, counts, named vendors, hedges a headline dropped).
          7. Audit and publish. The Verifier issues a verdict per item and reports what changed since the last run. A validator rejects any malformed briefing. The result is committed and the page redraws from it.

          Correlation, action, impact, scenarios

          The residents start the inquiry without being asked: the scheduled run fetches, correlates and grades before anyone looks. Each run also correlates items across domains (sector, actor, technique, vendor, policy) and writes, for the main stories, an action now, an impact chain, and three scenarios with what would confirm each. Likelihood uses words, not numbers, because there is no base rate behind them; the scenarios are the residents' reasoning from the bundle, labelled as such, not forecasts. The Geopolitical Analyst adds a per-theatre, per-layer (IT, OT, PIT) reading of the conflicts in the bundle and lists the theatres absent from the feeds, so silence is explicit.

          How "right, wrong, important" are kept apart

          Importance is the severity badge: OT or physical impact first, then US energy relevance, actor capability, scale, and whether action is possible. Correctness is the trust line and the Verifier's verdict: source tier, independent corroboration, claim-versus-confirmed, direct-source match. They are separate columns on purpose. An item can be critical and poorly confirmed, or fully confirmed and minor.

          Standing rules

          • Never invent incidents, numbers, victims or attributions. If the bundle does not cover it, say so.
          • Legal and regulatory claims need the primary document or the label [unverified]. Trade press is discovery only.
          • Vendor threat intelligence is attributed by name and flagged as coming from a firm that sells security products.
          • Attacker and leak-site claims are claims. "I cannot verify this" beats a plausible guess.
          • For every incident: who was not affected, and what else was happening at the same time.

          How the residents learn where to ask

          Each run records which sources supplied items, which primary hosts were reached, and which pages blocked the puller. The Librarian reads that record and reroutes the next run's questions (for example, statute questions to congress.gov rather than waiting for trade press). The map she keeps is agents/where_to_look.json, editable by hand.

          Cost, inputs and outputs of one run

          Input is the fetched bundle: about 25 energy-cyber stories and 30 wider stories as title, summary, source and bias note, roughly 4,600 tokens, plus each resident's rules (about 670 tokens). The fetch and the direct-source pull are plain HTTP: zero model tokens, 20 to 40 seconds, about 2 MB. Output is the briefing file: seven residents' briefings, answers and bubbles, up to 12 structured records, seven conversations, the audit, about 10,000 tokens.

          One run on the Claude API is about 44 calls, roughly 234,000 input tokens and 10,500 output tokens. Because every call reads the same bundle, the bundle is sent as a cached system block, which cuts the input cost by about 90%. At Anthropic's first-party rates (cached): Sonnet 5.5 about $0.22 per run, $0.44 per day, $13 per month; Opus 5.5 about $0.40 per run, $24 per month; Haiku 5.5 about $0.01 per run, under $1 per month. Uncached, multiply by about 2.5. The run itself takes 3 to 6 minutes. The alternative, a claude.ai scheduled routine that does the curation as an agent session, uses more tokens (it reads files and runs scripts interactively) and is billed through the subscription rather than per token. The actual counts are written to usage in the briefing on every API run, so the estimate is checked against reality daily.

          How certain is it, and can it invent news?

          The model never fetches; the fetcher does, from a fixed list, and writes a file. The model only reads that file. So an invented story would have to be invented against a bundle that does not contain it, which the Verifier's cross-check catches because every claim must trace to a source line. The remaining risk is misreading, not inventing: compressing a hedge, over-weighting a vivid number, mislabelling IT as OT. That is what the direct-source pull and the agree/differ cross-check exist for, and it is why the trust line, the corroboration count and the Verifier's verdict sit next to every item. Certainty is stated per item, never for the briefing as a whole. The limitations tab lists what the system cannot know at all.

          Where the pieces live

          Allowlist: sources.json. Residents and rules: agents/personas.json. Record schema and taxonomy: agents/schema.json. Scripts: fetch_news.py, run_agents.py, pull_sources.py, validate.py. Playbook for the scheduled agent: CURATION.md. The page is static; it only reads docs/data/*.json.

          Limitations read before trusting anything here

          • Not live. The town shows a snapshot from the last scheduled run, not the internet right now. The top bar shows the age of the data and turns amber past 24 hours. Nothing needs a button: runs are scheduled twice a day. Only the chat becomes live if you add a key or proxy in Settings.
          • Absence of evidence is the biggest gap. "Who was not affected" can only be answered from what credible sources reported. If an operator was hit and did not disclose, the town will say "not affected" and be wrong. Silence in coverage is not safety, and the Contrarian says so, but the data cannot.
          • Verification is scheduled, not random. The cloud schedule allows fixed times, not random intervals. The playbook adds a random spot-check: each run re-pulls two items chosen at random, so a page that quietly changed is caught eventually, not instantly.
          • The fetch is only as good as the allowlist. CISA's feeds return 403 to automated clients and Utility Dive blocks the puller, so US government and utility-press items are under-represented and two legal items this week could not be checked against their text. NERC, Reuters, ENISA and Dragos have no working public RSS.
          • Relevance is a keyword rule. A story needs an energy term and a cyber term. That misses stories that use neither (a vendor name only) and admits some that use both loosely. The Contrarian and Verifier exist partly to catch this.
          • The curator is a language model. It can misread a summary, over-weight a vivid detail, or compress hedged language. The rules, the direct-source pull and the cross-check reduce this; they do not remove it. Today's briefing was curated in a live session rather than by the scheduled run, and the model field says so.
          • Vendor-funded outlets dominate OT coverage. The Media Critic flags it every day; it does not change the fact that much ICS reporting originates with firms selling the fix.
          • English-only, US-first by construction. The source list decides the geography. A French victim statement was reachable but the English keyword matcher found nothing in it; it was read by hand.
          • No private or member-only data. E-ISAC, ONG-ISAC and paywalled journals are listed in Where to look but never read.
          • It does not predict. Severity ranks what is known; it is not a forecast of what will be attacked.
